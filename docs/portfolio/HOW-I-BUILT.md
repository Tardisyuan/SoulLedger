## 1. 这是什么，我在里面做什么

SoulLedger 是一个全栈系统：Django + DRF 后端、Next.js 网页、一个共享的平台无关层（`packages/core`）、
两个 Expo 原生 App，追踪灵魂在四种神话体系（中国、欧洲、埃及、希腊）里的审判与轮回。
架构见 [`README.md`](../../README.md#系统架构)，关键取舍见 [`docs/adr/`](../adr/README.md)。

分工（待作者确认措辞）：

- **我定规则和方向**：领域模型怎么建（四种文明不是一个模型换皮）、什么算做完、哪些事不做。
- **AI（Claude Code）写大部分代码**，并按我定的规则在仓库里留下测试和注释。
- **我审、我验、我拍板**：每一轮由我读结果、看门禁退出码、决定合不合；设计稿由 Claude Design 出，我来取舍。

## 2. 怎么跟 AI 协作

不是「说一句话等代码」。做法是把规则写进仓库，让每一轮都在同一套约束里：

- **规则写在 `CLAUDE.md`**：怎么跑门禁、哪些命令会撒谎、提交格式、什么叫「验证过」。
  其中最重要的一条：没有执行证据，不许写「已修复 / 已验证 / 可上线」；报通过数必须带命令、退出码和数量。
- **先写根因再修**：症状 → 根因 → 方案，根因不明就明说，不打补丁掩盖。修完检查同一根因在别处有没有。
- **新检查必须先证明会红**：把它守护的东西改坏，看它变红，再信它的绿。
- **子代理只写代码，不当裁判**：它们并行干活，但「全绿」要在合并后的树上由主会话统一跑。
- **审计是一种固定动作**：多路只读审查，产出台账，逐条关闭，再给每一类问题补一道守卫。

## 3. 几个真实事故（以及它们变成了什么规矩）

每一条都在 `CLAUDE.md` 或提交历史里能查到。

### 3.1 「Production Ready」的报告，三个月后被审计推翻

2026-05-30 的一份报告写着「Production Ready / Security 8.5」；2026-08-07 的审计在同一份代码里找到
4 个租户隔离的严重缺口，之后一个月里有 61 个修复提交在补上一次修复漏掉的东西。
**规矩**：文档里的「完成」不是事实来源，提交历史和可执行的检查才是；没有执行证据不许宣称。
**结构性修法**：把租户过滤收口成一个函数，加元测试钉住每个 ViewSet（[ADR 0001](../adr/0001-tenant-isolation-in-the-view-layer.md)）。

### 3.2 SQLite 全绿，真 PostgreSQL 上第一次就出两个缺陷

2026-08-27，2,665 条测试全绿的代码第一次碰真 PostgreSQL，当场暴露两个：失败语句会中止事务（SQLite 不会），
所以 `except: pass` 在测试里是空操作、在迁移里却能杀死整个事务；`varchar(500)` 的列装不下 524 字符的常量
（SQLite 不检查长度）。
**规矩**：碰事务、约束、列宽的改动，必须在真 PostgreSQL 上再跑一遍；只在 PG 上有意义的测试列成名单并钉住。
见 [ADR 0003](../adr/0003-gates-select-tests-and-run-remotely.md)。

### 3.3 子代理在陈旧的树上报「全绿」

一轮里五个并行子代理，四个的工作目录停在旧的 `main`，不含当时分支上已有的十几个提交。
一个代理报告「2530 全绿」，绿在一棵没有本轮任何工作的树上，重跑才是 2574；
另一个代理报告了一个其实已经修好的缺陷，这句话还被写进了提交信息；
第三个在陈旧的树上量覆盖率，把门槛棘轮到了「守得住是运气不是验证」的数。
**规矩**：每个子代理动手前先确认在分支尖端；所有门禁数字必须在更新后的树上重跑。

### 3.4 子代理的定向测试是绿的，合并后全量红

同一个形状出现三次：迁移改了读写分支，定向测试全过，合并后全量 18 条红；
补了一个事件类型，定向 2,284 条全过，真 PG 全量 7 条红（前端有一道守卫要求每个事件类型都有标签和三份语言包的词条）。
**规矩**：「N passed」只说明它跑的那部分；改了枚举、迁移、文案、路由的，合并后先跑全量门禁再推送。

### 3.5 退出码被管道吞掉

`ruff check . | tail -1` 在失败时显示的是「1 fixable」而不是「Found 1 error」，`cmd | tail` 的退出码是 `tail` 的，永远是 0。
两条 lint 错误因此躺在 main 上，一次 Playwright 的「3 failed」被读成了绿。
**规矩**：读退出码，不读输出。

### 3.6 为了「500 行」拆文件，反而制造了漂移

一次为满足行数上限拆了十六个文件，留下一个转发垫片、四处过期引用和一条「42 条测试」的记录，
后来它不等于任何文件也不等于任何总和。仓库现在的规则是：拆分要有缺陷来论证，不能只靠数字。

## 4. 审计闭环

做法是固定的：多路只读审查 → 台账（每条有严重度和证据）→ 逐条修复 → 为每一类补一道守卫 → 台账归档。

| 日期 | 范围 | 结果（台账保存在本地，不在仓库） |
|---|---|---|
| 2026-08-29 | 全量审计 | 181 条（严重 22、高 46、中 69、低 44），2026-08-31 全部关闭 |
| 2026-11-11 | 租户、权限、一致性等 | 41 条，当日修完并推送 |

这两个数字来自作者的项目记录；公开仓库只保留了守卫测试和提交，台账全文有意不公开（含漏洞细节）。

## 5. 门禁：怎样让「绿」可信

- 一个脚本管推送前的全部检查，只测改动影响到的部分，整轮跑在一台独立的构建机上，
  真 PostgreSQL 单独一条路径（[ADR 0003](../adr/0003-gates-select-tests-and-run-remotely.md)）。
- 数字随时过期，所以文档里的测试数都带日期。最近一次落在落地页数据里的读数（2026-11-06）：
  后端 9,243、网页 5,677、灵魂端 1,204、官员端 1,095、E2E 约 270（见 `frontend/src/config/landing-stats.json`）。

## 6. 没做好、有意没做的

- CI 不在每次推送上跑（额度耗尽过），改为每天一次，所以最坏情况下 CI 红要晚一天才发现。
- 按租户分库只有方案没有代码，所有关于未来负载的说法都标了「未量」。
- 展示站是纯前端回放，不是线上系统（[ADR 0005](../adr/0005-demo-site-is-a-frontend-only-replay.md)）。
