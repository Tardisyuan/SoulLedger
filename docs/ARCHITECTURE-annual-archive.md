# 年度归档(设计稿,2026-10-30,未实现)

用户 2026-10-30 定:`SoulEvent` 事件日志、审判与账号数据**不删**。不删的表只会变大,所以需要一条
「把旧年份搬离热库、但仍可查」的路。本文只写设计;标「待定」的几处等用户拍板再做。

## 1. 归档什么

| 候选 | 理由 | 体量来源 |
|---|---|---|
| `SoulEvent`(事件日志) | 只增不改,查询几乎都看近期;业务记录 | 每次审判 / 处置 / 轮回各若干行 |
| `AuditLog`(超过保留窗口前) | 现在到期直接删(`AUDIT_LOG_RETENTION_DAYS`,默认 365);归档可以把「删」改成「搬」 | 每次写操作一行 |
| 已结案的 `Judgment` 及其子表(评议、引用、证据、上诉、附件元数据) | 结案后只读 | 按案件数 |
| 已完成轮回的 `Soul` 链路(处置、轮回记录) | 只读 | 按灵魂数 |

**待定 A:**归档范围是只有 `SoulEvent` + `AuditLog`(纯日志,搬走不影响任何外键),还是连同已结案的
业务行。后者要处理外键:被归档的案件仍被灵魂、通知、事件引用,要么整条链一起走,要么在热库留一行「墓碑」。
建议第一期只做两张日志表。

## 2. 怎么切

- 按**自然年**切(UTC),年份结束后满 N 个月(**待定 B**,建议 3 个月,给迟到的更正与上诉留余地)再归档。
- 按租户分文件:各殿的数据各自一份,将来按殿交付或销毁不必拆文件。
- 一次归档 = 导出 → 校验 → 删除热库行,三步分开:导出写一个清单(行数 + 每个文件的 sha256),
  校验从归档里读回并比对行数与抽样内容,通过后才分批删(同 `apps/audit/retention.py` 的 `_raw_delete`,不写审计行,
  但归档本身写一条审计「某年某殿 N 行已归档到 X」)。
- 做成登记在 `apps/scheduler/registry.py` 的按租户任务(每年 1 次,也可手动运行),运行记录在 `/scheduler`。

## 3. 存哪

**待定 C:**三种选法,建议第一种。

1. **同一 PostgreSQL 里的归档 schema / 分区表**:`SoulEvent` 按年分区,旧分区 `DETACH` 后挪到 `archive` schema。
   查询仍是 SQL,备份随主库;代价是库的体量不减,只是热表变小。
2. **对象存储里的文件**(Parquet 或 gzip 的 JSON Lines,每租户每年一个,外加清单):热库真正变小;
   查时要另起读取工具。需要定:存哪个桶 / 哪台机器(现有 unRAID?)、是否加密(建议用独立于 `ENCRYPTION_KEY` 的归档密钥)、
   保存多少年。
3. 独立的归档库(另一个 PostgreSQL 实例):隔离最好,运维成本最高。

## 4. 谁能查

**待定 D:**

- 建议:只读,且只给 ADMIN(全局)与该殿的 ADMIN(本殿);新权限码 `archive.read`,默认不授予其它角色。
- 查询形式:按「年 + 租户 + 灵魂 / 案件编号」检索,返回与在线详情页同形的只读视图;或只提供导出下载。
- 每次查归档写审计(谁、查了哪年哪殿哪个对象)。
- 灵魂端(App)看不到归档:灵魂的「我的一生」只看热库;要不要给灵魂看自己的归档记录,一并待定。

## 5. 不做的

- 不在归档时改写或脱敏内容:归档是搬家,不是加工。脱敏 / 销毁是另一条规则(法规或用户要求时再定)。
- 不归档运行数据(通知、推送、webhook 投递、会话):它们按 `docs/DEPLOYMENT.md`「数据保留」到期即删。
