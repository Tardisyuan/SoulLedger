# SLO 与错误预算策略

> **这是文档,不是执行中的制度(用户 2026-11-14 决定)。** 这里没有生产流量,也没有值班的人;
> 下面每一条 SLO 都**没有在量**,也没有任何告警会因它而响。它写的是「如果上线,这套部署形态
> 能守住什么、守不住时怎么办」。网页 `/about/system` 的第二块照抄这张表,标作「目标,不是读数」。
> 设计依据:`docs/audit/2026-11-14-expert-design/raw/be-obs.md` §3.1(本地,未进 git)。

## 要真的执行,还缺什么

1. **数据源**:请求计数与耗时直方图 2026-11-14 起有了(`TraceIdMiddleware` → `backend/apps/core/obs.py`,
   进程内累加、定时刷进 Redis 小时桶,`/metrics/` 导出),但按「方法 + 路由模板」计,**还不按旅程**;
   桶边界含下表全部延迟阈值(`tests/test_obs_request_metrics.py` 守着)。没有任何东西在抓它、按窗口算比例。
2. **旅程映射**:`JOURNEYS = {"<view_name>": "open_desk", …}`,按 `resolver_match.view_name`,不按 URL。
   具体视图名**没有逐个核对**。未列入的请求归 `other`,只计数不设目标。
3. **告警出口**:燃烧率由一个定时任务算,超线就给 ADMIN 发站内通知(复用 `apps/scheduler` 的
   `last_alerted_at` 去重)。没有 PagerDuty,也不打算接。
4. **一个会遵守策略的人**:「预算用完停功能」对一个人的项目是自我约束,没有任何东西拦着合并。

在这四件事之前,这张表只能拿来对照设计,不能拿来判断系统好坏。

## 窗口与目标

- 窗口:**28 天滚动**(40 320 分钟)。
- 可用性目标定 **99.5%**,不是 99.9%:单机 compose、没有高可用,一次部署重启就吃几十秒;
  99.9% 在 28 天里只有 40.3 分钟,是写给人看的数字。

| 目标 | 28 天里允许坏的比例 | 折成整段停机 |
|---|---|---|
| 99.5% | 0.5% | 201.6 分钟 |
| 99%   | 1%   | 403.2 分钟 |
| 95%   | 5%   | 2 016 分钟(只用于延迟类,不折成停机) |

## SLO 表

SLI 一律写成「好事件 / 有效事件」。4xx 算好事件:那是用户或权限的问题,不是服务的。

| # | 旅程 | SLI(好事件 / 有效事件) | 目标 |
|---|---|---|---|
| A1 | 开卷(判官进 `/desk`:案件列表 + 打开一卷) | 非 5xx 的请求 / 全部请求 | 99.5% |
| A2 | 开卷 | 耗时 ≤ 400 ms 的请求 / 非 5xx 请求 | 95% |
| B1 | 落印(提交裁决) | 非 5xx / 全部 | 99.5% |
| B2 | 落印 | 耗时 ≤ 800 ms / 非 5xx | 95% |
| B3 | 落印 · 正确性 | 当日已落印且有对应 `SoulEvent` 行的判决 / 当日已落印判决 | 100% |
| C1 | 灵魂端时间线(`/api/v1/me/` 读) | 非 5xx / 全部 | 99.5% |
| C2 | 灵魂端时间线 | 耗时 ≤ 500 ms / 非 5xx | 95% |
| C3 | 灵魂端时间线 · 新鲜度 | 入队后 60 秒内发出的推送 / 全部推送 | 99% |
| D1 | 实时(站内通知经 WebSocket) | 在线连接上 5 秒内送达的事件 / 发往在线连接的事件 | 99% |
| E1 | 定时任务 | 计划时间后 5 分钟内启动且成功的运行 / 应有的运行 | 99% |
| E2 | 事件 webhook | 5 分钟内投递成功 / 全部投递 | 99% |

- B3 的 100% 由「事件日志写在业务的同一事务里」保证(CLAUDE.md「事件日志是业务记录的一部分」);
  每日对账只为发现破例,预算为 0。
- C2 的 500 ms 与 `docs/ARCHITECTURE-tenant-sharding.md` 「只读压力」那条拆分触发线是同一个数。

## 燃烧率告警(多窗口)

燃烧率 = 窗口内坏事件比例 / (1 − 目标)。燃烧率 1 恰好在 28 天末用完预算。

| 告警 | 条件 | 含义 | 处理 |
|---|---|---|---|
| 快烧 | 1 小时窗口燃烧率 ≥ 14.4,且 5 分钟窗口也 ≥ 14.4 | 一小时烧掉 28 天预算的约 2% | 立刻处理 |
| 慢烧 | 6 小时窗口燃烧率 ≥ 6,且 30 分钟窗口也 ≥ 6 | 6 小时烧掉约 5% | 当天处理 |

短窗口那一半是为了故障停止后告警能自己消掉,不至于一直响到长窗口滚过去。

## 错误预算策略

- 预算剩余 ≥ 25%:照常。
- 预算剩余 < 25%:只合修复与可靠性改动;功能分支不合 main。
- 预算用完:停功能,直到窗口内预算回到 0 以上。
- 一次事故吃掉 ≥ 20% 的预算:写一页事后记录(经过、根因、修复、同类根因是否还在别处),放在 `docs/`。
- 预算富余不是「可以更随便」的理由;它只说明目标定得可能太松,下一次复盘时再议。
