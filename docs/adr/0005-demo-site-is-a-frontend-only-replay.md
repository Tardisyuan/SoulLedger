# ADR 0005: The public demo is a front end replaying recorded API answers, with no backend

Status: accepted (2026-11).

## Context

A visitor should be able to try the product without an account, and every visitor should see the same world. A live back end
would need hosting, data cleanup after each visitor, rate limiting, and protection against abuse, and it would tie the
demo's availability to a server that has no production deployment of its own.

## Decision

1. The demo is the real front end built with one switch, `NEXT_PUBLIC_DEMO_MODE=1`. Without the switch the code paths are
   dead-code-eliminated, and a test plus a bundle check confirm the demo code never reaches a normal build.
2. At run time the HTTP layer is replaced: axios gets another adapter, `fetch` is wrapped for `/api/v1/` paths, and
   `WebSocket` becomes a stand-in that reports "connected" and stays silent. No service worker, no network.
3. Reads are answered from JSON recorded from the real back end: six roles, two languages, every page walked and every GET
   declared by the OpenAPI schema swept. Tokens and secret-named fields are removed from the recording.
4. Writes go to a per-tab overlay (`sessionStorage`) with generic create/patch/delete plus hand-written handlers for the main
   flows that must move state like the server. Signing in or out resets the overlay, so each visitor starts from the same world.
5. The recording is regenerated by a script, and it re-records only when its inputs changed (hash of seed, backend apps,
   lock file and the recording script).
6. Where the demo cannot honestly do something, it says so (a banner on every page; unknown reads come back empty and log a
   console line rather than erroring).

## Consequences

- Zero server cost, no data to clean, and the demo cannot be used to attack anything.
- The demo is a recording, not the system: server-side rules (permission denials, concurrency conflicts) appear only where they were
  recorded or hand-modelled. The write handlers are a second implementation that can drift from the back end; the recorded schema
  sweep and an end-to-end demo suite are the check on that.
- Re-recording needs the heavy back end stack, so it runs on the build machine, not on the laptop.
- The same property is a talking point: the whole product flow runs with no back end, and the OpenAPI schema is what makes the
  recording exhaustive.
